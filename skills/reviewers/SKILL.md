# Ревьюеры

Задача — найти реальные проблемы в работе до того, как она уйдёт дальше, и понятно о них сообщить. **Ревьюеры ничего не исправляют**: не правят файлы, не делают коммитов, не ставят пакеты. Только замечания с приоритетами и подсказкой, что сделать. Если пользователь после ревью попросит исправить — это отдельная задача, не часть этого скилла.

Пиши на русском, простыми словами; термины поясняй при первом упоминании.

## Ревьюеры

| Ревьюер | Что ищет | Инструкция |
|---|---|---|
| code-reviewer | Баги, ошибки логики, необработанные ошибки, проблемы с путями и кодировкой в Windows | `references/code-reviewer.md` |
| test-reviewer | Тесты, которые не могут упасть или проверяют не то; пропущенные случаи; предлагает мутации | `references/test-reviewer.md` |
| stats-reviewer | Неподходящие методы, малые выборки, неверное чтение p-value, причинность из корреляции | `references/stats-reviewer.md` |
| privacy-security-reviewer | Секреты в коде, уязвимости, лишний сбор и утечки личных данных | `references/privacy-security-reviewer.md` |
| design-reviewer | Шаблонный «ИИ-интерфейс», иерархия, контраст, тексты интерфейса | `references/design-reviewer.md` |

## Шаг 1. Что проверяем

- **Claude Code, есть git.** Определи объём (только командами чтения):
  - незакоммиченные изменения: `git status --short`, `git diff HEAD`;
  - ветка целиком: `git diff main...HEAD` (или `master`) и `git log --oneline main..HEAD`;
  - pull request или конкретные файлы — если пользователь их назвал.
  Пустой дифф или непонятно, что проверять, — спроси одной фразой. Не проверяй «наугад весь проект».
- **claude.ai или без git** — проверяется то, что пользователь вставил или приложил: код, текст, таблицу, скриншот, описание.
- Узнай, **зачем** изменение (из сообщения, описания PR, коммитов) — ревьюеру нужен замысел, чтобы отличить ошибку от решения.

## Шаг 2. Выбор ревьюеров

Если пользователь назвал ревьюеров — бери их. Иначе выбери по содержимому:

| Признак в изменениях | Ревьюер |
|---|---|
| Любой исходный код (`.py`, `.js`, `.ts`, `.cs`, `.go`, `.ps1`…) | code-reviewer |
| Тесты (`tests/`, `test_*.py`, `*_test.py`, `*.spec.ts`, `*.test.js`) **или** новая логика без тестов | test-reviewer |
| Анализ данных, `.ipynb`, расчёты по таблицам, выводы с цифрами, A/B-тесты, p-value, графики с выводами | stats-reviewer |
| Пароли, токены, ключи, `.env`, вход и права доступа, личные данные, сетевые запросы, SQL, запуск команд, загрузка файлов, зависимости, настройки CI | privacy-security-reviewer |
| Интерфейс: HTML, CSS, JSX/TSX, Vue, Svelte, шаблоны страниц, скриншоты, макеты, тексты кнопок и сообщений | design-reviewer |

Одной строкой скажи, кого выбрал и почему, и кого нет («stats-reviewer не нужен — в изменениях нет анализа данных»). Сомневаешься — лучше включить ревьюера, чем пропустить.

## Шаг 3. Запуск

Каждому ревьюеру дай: объём (список файлов и как получить дифф или сам текст), замысел изменения и напоминание «только сообщай замечания, ничего не меняй».

1. **Есть субагенты-ревьюеры** (Claude Code с установленным плагином: агенты `code-reviewer`, `test-reviewer` и т. д., иногда с приставкой, например `kit:code-reviewer`) — запусти выбранных параллельно. **Всегда**, даже на маленьком диффе: независимый взгляд — смысл ревью. Сам проходи роли, только если инструмента субагентов (Agent/Task) нет.
2. **Есть инструмент субагентов, но таких агентов нет** (например, скилл подключён через claude.ai) — запусти субагентов общего назначения параллельно; каждому передай полный текст его инструкции из `references/` и объём проверки.
3. **Субагентов нет** (обычный чат claude.ai) — пройди ревьюеров по очереди: перед каждым прочитай его инструкцию из `references/`, начни раздел с «Ревьюер: …» и проверяй только свою область.

Если субагент упал, не ответил или проверил не всё — это **непроведённая проверка**, а не «замечаний нет». Так и напиши.

**Тесты не запускай** без просьбы пользователя: запуск создаёт служебные файлы (`__pycache__`, `.pytest_cache`) и может менять данные. Если запуск нужен для вывода — только `python -B -m pytest -p no:cacheprovider` (или аналог без записи кеша), и сравни `git status` до и после: ревью не должно оставлять следов.

## Шаг 4. Сведение

1. **Убери дубли**: одна проблема, найденная двумя ревьюерами, — одно замечание с пометкой обоих.
2. **Перепроверь серьёзное**: каждое «критично» и «важно» сверь с кодом сам — открой файл и строку. Не подтвердилось — убери. Ложные тревоги подрывают доверие ко всему отчёту.
3. **Убери замечания без доказательств**: каждое должно указывать место (файл и строку, абзац, элемент экрана) и объяснять, что сломается. Номера строк бери из самого файла (чтение с номерами), а не из заголовков диффа.
4. **Откалибруй приоритеты.** «Критично» — ломается основной сценарий, нет обходного пути, утечка секрета или данных, выполнение чужих команд. Проблема настройки при рабочей альтернативе (например, тесты запускаются через `python -m pytest`, но не через `pytest`) — «Важно». Нереалистичные входные данные — «Мелочь». Итог отчёта соразмерен найденному: для почти чистого изменения — «можно коммитить после мелких правок», а не «исправьте критичное».
5. **Мелочей — не больше 3 на ревьюера.** Вкусовщину без последствий не включай.
6. **Мутации не выбрасывай.** Если работал test-reviewer, его 1–3 главные мутации, которые тесты не поймают, идут в отчёт отдельным разделом.
7. **Термины поясняй** в скобках при первом упоминании, а для Windows давай готовые команды PowerShell там, где они нужны для исправления (например, переменная окружения: `$env:ИМЯ = "значение"` в PowerShell и `os.environ["ИМЯ"]` в коде).

## Формат отчёта

```
**Проверено:** <что именно: ветка/файлы/текст> · **Ревьюеры:** <кто работал> · **Не проверялось:** <что и почему>

**Итог:** <можно двигаться дальше / сначала исправить критичное / нужна переделка> — <одна фраза почему>

### Критично (исправить до слияния или публикации)
1. [code] `app/db.py:42` — <что не так>. <Чем грозит>. Что сделать: <подсказка словами>.

### Важно
…

### Мелочи
…

### Мутации, которые тесты не поймают (если работал test-reviewer)
- `функция`: <мутация> → тесты пройдут. Добавить тест: <вход → ожидаемый результат>.

### Что сделано хорошо
<1–2 пункта, только если есть что сказать по делу>
```

Шапка («Проверено · Ревьюеры · Не проверялось») и «Итог» нужны всегда, даже если работал один ревьюер. Если замечаний нет — так и скажи: «Серьёзных проблем не нашли», и перечисли, что именно проверено. Не выдумывай замечаний ради объёма.

## Чем отличается от встроенных команд Claude Code

В Claude Code есть встроенные `/code-review` (баги в диффе) и `/security-review` (безопасность ветки). Этот скилл добавляет ревьюеров тестов, статистики и дизайна, работает в claude.ai без git и всегда только сообщает — ничего не правит. Если пользователь просит именно встроенную команду, не подменяй её этим скиллом.

## Пример (сокращённо)

Пользователь в Claude Code: «Проверь ветку перед слиянием». В диффе — `report.py` (новая функция `orders_between(start, end)` для отчёта о заказах за период) и `tests/test_report.py`.

> **Проверено:** ветка `feature/report` относительно `main`, 2 файла · **Ревьюеры:** code, test · **Не проверялось:** stats, design, privacy-security — нет анализа данных, интерфейса и личных данных.
>
> **Итог:** сначала исправить критичное — отчёт теряет заказы последнего дня.
>
> ### Критично
> 1. [code] `report.py:14` — условие `order.date < end` не включает последний день периода: отчёт «за октябрь» с `end = 31 октября` не покажет заказы 31-го. Что сделать: сравнивать `<=` или передавать конец как начало следующего дня — и написать это в описании функции.
>
> ### Важно
> 1. [test] `tests/test_report.py:8` — тест подменяет (mock — подделка части программы) весь список заказов и проверяет только, что функция вернула список. Настоящий отбор по датам не выполняется.
>
> ### Мутации, которые тесты не поймают
> - `orders_between`: `<` → `<=` или `>=` → `>` — тесты пройдут. Добавить тест: заказы 1, 15 и 31 октября, период 1–31 октября → все три заказа.
>
> ### Что сделано хорошо
> - Даты сравниваются как даты, а не как строки — порядок «2026-10-09» и «2026-10-10» не перепутается.
