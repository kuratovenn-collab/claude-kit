# Признаки качества и тревожные признаки в отчётах

Используй как чек-лист. Каждое замечание в ответе привязывай к конкретному месту отчёта. Признак — повод проверить, а не приговор: у «тревожного» признака может быть честное объяснение в том же отчёте.

## Признаки качественной работы

| Признак | Как выглядит |
|---|---|
| Доказательства вместо слов | Приведён вывод команд: `18 passed, 0 failed`, `Build succeeded`, код выхода 0 |
| Конкретика | Названы файлы, функции, коммиты (хеши вроде `a1b2c3d`), ветка, ссылка на pull request |
| Объём совпадает с задачей | Изменено то, что просили, и не больше; есть объяснение, если пришлось тронуть что-то ещё |
| Честность о недоделках | Отдельный раздел «не сделано / ограничения / не удалось проверить» с причинами |
| Решения объяснены | «Выбрал X, потому что Y» — особенно там, где задача была неоднозначной |
| Воспроизводимость | Есть шаги, как проверить самому: команды, что должно получиться |
| Тесты на новое поведение | Добавлены тесты на то, что изменилось, а не только «старые тесты проходят» |
| Проверка исправления бага | Описано, как баг воспроизводили до исправления и что после него он не повторяется |
| Следующий шаг | Предложено, что делать дальше, и названы риски |

## Тревожные признаки

### Успех без доказательств
- «Должно работать», «тесты должны пройти», «вероятно, исправлено», «готово» — без вывода команд.
- «Проверил» — но не сказано как.
- Заявление противоречит логам: в выводе есть `FAILED`, `Error`, `Traceback`, `exit code 1`, а текст говорит «всё прошло».
- Цифры не сходятся: «все 20 тестов прошли», а в выводе 18 строк.

### Тесты ослаблены
- Тест отключён, пропущен или удалён: `skip`, `xfail`, `@pytest.mark.skip`, `it.skip`, `@Disabled`, тест закомментирован.
- Тест изменён так, чтобы проходить: поменяны ожидаемые значения под новый результат без объяснения, почему старые были неверны.
- Проверка заглушена: `assert True`, пустой тест, всё подменено заглушками (mock — подделка части программы для теста), так что настоящий код не выполняется.
- Пропуск проверок при коммите: `--no-verify`, отключённый линтер, `# noqa`, `// @ts-ignore`, `eslint-disable` без причины.

### Выход за рамки задачи
- Рефакторинг (переписывание без изменения поведения), «заодно улучшил», «для единообразия» — в файлах, которые не относились к задаче.
- Новые зависимости (библиотеки) без объяснения, зачем.
- Удалены файлы или функции, о которых не просили.
- Изменены настройки проекта, CI, правила форматирования без запроса.

### Временные решения и долги
- «Временно», «потом исправим», `TODO`, `FIXME`, `HACK` в новом коде.
- Жёстко прописанные значения (hardcode): пути `C:\Users\…`, пароли, адреса серверов, «магические числа».
- Ошибки молча проглатываются: `except: pass`, `catch {}`, «добавил try/except, чтобы не падало».

### Опасные действия
- `git push --force`, переписывание истории, `reset --hard`, удаление веток.
- Пароль, токен, ключ API в коде, в отчёте или в коммите.
- Изменения напрямую в `main` вместо отдельной ветки, если просили ветку.
- Отключены проверки безопасности, расширены права доступа без объяснения.

### Умолчания
- Из исходной задачи не упомянуты некоторые пункты — ни как сделанные, ни как несделанные.
- Нет ни слова о проверке — ни что проверено, ни что не удалось.
- Отчёт очень длинный и гладкий, но без единой команды, файла или числа.

## Как оценить доверие

- **Высокое** — ключевые утверждения подкреплены выводом команд, объём совпадает с задачей, недоделки названы.
- **Среднее** — работа правдоподобна, но часть утверждений без доказательств или есть небольшой выход за рамки.
- **Низкое** — успех заявлен без доказательств, тесты ослаблены, логи противоречат тексту или есть опасные действия.
